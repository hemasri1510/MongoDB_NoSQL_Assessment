    Activity 8.1: Why Use an Arbiter?
    
          
    
            
    
              Majority Quorum Math: A MongoDB replica set requires a strict majority of voting members (⌊N/2⌋ + 1) to elect or sustain a Primary.
            
    
            
      
              
    • With 2 data nodes, majority is 2. If 1 node fails, only 1 vote remains → the surviving node steps down to SECONDARY (no writes possible!).
      • 
              
    • Adding a 3rd voting Arbiter creates 3 total votes (majority = 2). If 1 data node fails, the surviving data node + arbiter = 2 votes, preserving Primary election capability.
      • 
              
    • Zero Storage Overhead: Arbiters hold no user data, process no oplog replication, and require minimal RAM/CPU.
      •

    Architectural Explanation & Activity 9.1 Analysis
    
        
      
          
    • w:1 (Fastest — 2–5x faster than w:majority): Returns immediately once the Primary applies the write to its in-memory WiredTiger cache. Zero network wait for secondaries.
      • 
          
    • w:majority: Primary must write locally AND replicate the oplog entry over the network to at least 1 Secondary (2 of 3 voting members), adding 1 network round-trip + secondary oplog apply time.
      • 
          
    • w:all (w:3): Must wait for every data-bearing node in the replica set to acknowledge; latency is bounded by the slowest secondary (tail latency).
      • 
          
    • Activity 9.1 (j:true vs j:false): Yes — enabling j:true adds significant latency (~1.5–2.5 ms/write, often 2x–4x total runtime) because MongoDB must synchronously fsync the on-disk journal before returning rather than batching background journal commits every ~50–100 ms.
      • 
        
    
      
    

      
    
        
    Python Benchmark Script (write_concern_benchmark.py)
    
        
    from pymongo import MongoClient, WriteConcern
import time

client = MongoClient("mongodb://localhost:27017,localhost:27018,localhost:27019/?replicaSet=rs0")
db = client["cti_write_concern_lab"]

for w_val in [1, "majority", 3]:
    for j_val in [False, True]:
        coll = db.get_collection("bench", write_concern=WriteConcern(w=w_val, j=j_val))
        t0 = time.perf_counter()
        for i in range(1000):
            coll.insert_one({"seq": i, "w": str(w_val), "j": j_val})
        dt = time.perf_counter() - t0
        print(f"w:{w_val}, j:{j_val} -> Total: {dt:.3f}s | Avg: {(dt/1000)*1000:.2f}ms")

    Activity 11.1: MongoDB 5.0+ Live Resharding (reshardCollection)
    
        
      
          
    1. Create Supporting Index: Build an index on the new shard key (e.g., db.orders.createIndex({customer_id: "hashed"})).
      2. 
          
    2. Initiate Online Resharding: Run db.adminCommand({ reshardCollection: "ecommerce.orders", key: { customer_id: "hashed" } }) on mongos.
      3. 
          
    3. Parallel Clone & Oplog Tail: MongoDB creates recipient chunks across shards, clones existing documents in parallel, and continuously applies live oplog writes during cloning.
      4. 
          
    4. Brief Metadata Cutover: Acquires a short write lock (~seconds) to swap collection metadata and drops the old collection copy.
      5. 
        
    
      
    
      
    
        
    Resharding Limitations & Operational Constraints
    
        
      
          
    • Disk Space Overhead: Requires ~1.2x–2x temporary storage headroom across shards while the cloned copy coexists with the original.
      • 
          
    • Single Concurrent Operation: Only one reshardCollection job can execute at a time in the cluster.
      • 
          
    • Unique Index Rule: Existing unique indexes must include the new shard key as a prefix.
      • 
          
    • Critical Section Timeout: Heavy write spikes or long-running transactions can abort the final cutover if reshardingCriticalSectionTimeoutMillis is exceeded.

    Engineering Report: Why Monotonic Keys Cause Hotspots & When Ranged Keys Are Appropriate
    
      
    
        
    
          
    Why Monotonically Increasing Keys Cause Hotspots
    
          
    
            Ranged sharding partitions data into contiguous [min, max) chunks. Because every new timestamp or auto-incrementing ID is larger than all previous values, 100% of incoming writes route to the single upper-bound chunk (ending at MaxKey) on one shard. Even when the balancer splits and migrates older chunks, active write traffic stays pinned to one shard—capping cluster insert throughput to single-node IOPS and CPU.
          
    
        
    
        
    
          
    When a Ranged Shard Key Is Still Appropriate
    
          
    
            Ranged shard keys remain optimal when the key has high cardinality and non-monotonic distribution (such as a compound key {tenant_id: 1, ts: 1} or {region: 1, customer_id: 1}) and the application requires efficient range scans ($gte/$lt), ordered sorting on the shard key without in-memory merge sorts, or Zone Sharding for data-residency compliance.

            (1) Executive Summary
            
    
              Across 1,00,000 multi-source threat and fraud records benchmarked over 10 runs (median latency), no single database wins every workload: Apache Cassandra delivers the fastest real-time batch ingestion (6.20 ms / 1k events) and contiguous target history reads (1.40 ms), Neo4j dominates 3-hop lateral spread and fraud-community detection (8.90 ms vs. 68.40 ms in MongoDB and 112.00 ms in Cassandra), and MongoDB leads daily analytical rollups (14.20 ms) while serving as the flexible operational document and false-positive cross-reference store. We therefore recommend a polyglot architecture anchored by MongoDB paired with Cassandra for high-velocity time-series ingestion and Neo4j for multi-hop graph traversal.
            
    
          
    
          
    
            (2) Methodology
            
    
              Data Volume: 1,00,000 threat & fraud records pulled/generated across 5 feeds (OTX_AlienVault, AbuseIPDB, MISP_Feed, PhishTank, Internal_SIEM).
    
              Query Patterns: Q1 Threat History (latest 25 events/target), Q2 Target & Spread (3-hop lateral traversal), Q3 Daily Volume Analytics (day × source aggregation), Q4 Real-Time Insert Throughput (1,000-event batch).
    
              Test Environment: Python benchmark harness executing 10 timed runs per query per database and reporting the median latency (ms).

    Lab 18.2: Capstone Comparative Analysis Report & Scalability Planner
    
      
    
        Synthesizes system architecture, schema modeling, query latency, developer ergonomics, operational complexity, and hardware sizing across 1M, 10M, and 100M transactions.
      
    

      
    
        1. Executive Summary & Final Recommendation:
    
        A polyglot persistence architecture anchored by MongoDB as the primary operational document, analytics, and false-positive adjudication store—paired with Apache Cassandra for high-velocity time-series ingestion (1.40 ms history reads; 6.20 ms 1k-event batch writes) and Neo4j for 3-hop lateral spread and fraud-ring community detection (8.90 ms vs. 68.40 ms in MongoDB and 112.00 ms in Cassandra)—achieves optimal end-to-end latency and horizontal scalability.
      
    

      
    
        
    
          MongoDB (Document Hub)
          
    Schema & Modeling
    
          
    Flexible BSON documents embedding STIX/IOC payloads, risk scores, and INR transaction metadata with compound index {target_id: 1, timestamp: -1}. Ideal for Q3 Daily Volume Analytics (14.20 ms) and cross-referencing Neo4j communities.
    
        
    
        
    
          Cassandra (Wide-Column)
          
    Schema & Modeling
    
          
    Query-driven partition table PRIMARY KEY ((target_id), timestamp, threat_id) with descending clustering order. Append-only LSM Memtable/SSTable writes deliver linear ingestion scalability without B-tree splits.
    
        
    
        
    
          Neo4j (Property Graph)
          
    Schema & Modeling
    
          
    Labeled nodes (:Actor), (:Target) with directed [:TARGETED] edges. Index-free adjacency traverses 3 hops in 8.90 ms and isolates dense fraud rings via Louvain modularity.
